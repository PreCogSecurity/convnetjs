# Release process

Releases are cut by pushing a `v*` tag. `.github/workflows/release.yml` does the
rest: it checks that the tag matches `package.json`, builds, lints, tests, and
publishes to npm with provenance.

## Before the first release using this workflow

The publish step authenticates to the registry with the job's OIDC identity
(npm **Trusted Publishing**), so no long-lived npm token needs to live in the
repository. That needs a one-time setup on the package:

1. As the package owner, create an npm automation token if you do not have one,
   and on the package page go to **Settings → Trusted Publishers**.
2. Add a publisher with:
   - **Package name**: `convnetjs`
   - **Organization or user**: the GitHub organization or user that owns the
     workflow (`PreCogSecurity`)
   - **Repository**: `PreCogSecurity/convnetjs`
   - **Workflow filename**: `release.yml`
   - **Environment**: leave blank unless you create one
3. Save the token when prompted. npm needs it once to configure the publisher; it
   is not stored in this repository.

Until that is done, the workflow still works if a classic `NPM_TOKEN` repository
secret exists, because `NODE_AUTH_TOKEN` is still passed through as a fallback.
Once Trusted Publishing is live, **delete that secret** — see the note in
`release.yml`.

## Cutting a release

```bash
# 1. work on a clean default branch
git checkout main
git pull --ff-only

# 2. bump the version and describe the change
npm version 0.3.1 -m "release 0.3.1"
# ...edit CHANGELOG.md so the top entry covers this release...

# 3. verify exactly what is about to be published
npm pack --dry-run
npm run lint
npm test

# 4. tag and push. the tag push is the release trigger.
git push origin main --follow-tags
```

The workflow fails closed if the tag version and `package.json` disagree, so a
mistyped tag will not publish the wrong version.

## What gets published

`package.json` sets `"files": ["build/", "src/"]`, so the tarball contains the
built bundle and the sources and nothing else — no tests, no demos, no Docker
files, no repository history.

`build/convnet.js` is regenerated by the `prepare` script on install and again by
the release workflow, so the published artifact always matches `src/`. Verify it
locally with:

```bash
npm run build && git diff --exit-code build/
```

That should be a no-op. If it is not, you have an uncommitted build artifact in
your tree.

## Notes

- `npm publish --provenance` attaches a signed attestation linking the published
  tarball to the commit it came from, so consumers can verify supply-chain
  provenance. This requires the `id-token: write` permission, which is the only
  elevated permission the workflow requests.
- The release job does not cancel in progress; two tags pushed at once should
  both complete rather than one cancelling the other.
